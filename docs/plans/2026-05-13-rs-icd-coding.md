# ICD-10 coding step in the SOAP-note pipeline

**Owner:** rs
**Date:** 2026-05-13
**Status:** In progress — skill + spawn implemented on the `icd10-coding` branch; not yet merged into `develop`. DB integration (see below) is pending the SQLite state-store plan landing.

## Goal

After the SOAP note `.md` is generated (or re-generated by Pre-chart), look up the relevant ICD-10-CM codes for each diagnosis and append a `## ICD-10-CM Codes` table at the end of the markdown file — **before** the `.docx` conversion runs. The end-of-doc table is the only placement for v1; per-doctor template-driven placement is a future iteration.

## Background

The user manually tested the flow in Claude Code desktop by pasting a finished `_soap_note.md` and asking it to find ICD codes via the **claude.ai ICD-10 Codes** MCP connector (`https://hcls.mcp.claude.com/icd10_codes/mcp`). The model used `search_codes` / `lookup_code` / `validate_code` and appended a clean markdown table that matched the format the user wants (see [docs/plans/icd-reference.png] — third screenshot in the conversation thread).

The connector is enabled at the org level, so any user logged into `claude` with their org account has it auto-registered (visible via `claude mcp list`). We add a project-scope `.mcp.json` fallback so the connector is wired even if the user's personal config is missing it.

## Approach

Mirror the existing skill / spawn pattern. One new skill, one new `spawnIcdCoding()` function, three replaced call sites.

### 1. Skill: `notes-claude/skills/add-icd-codes/SKILL.md`

**Prompt signature** (parsed in Step 1):

```
add ICD codes. Soap note: <abs-path>.
```

**Steps:**

- Step 0: permission boilerplate (Bash/Read/Write/Edit).
- Step 1: parse `Soap note:` path.
- Step 2: verify file exists; if a previous `## ICD-10-CM Codes` section is already present, strip it (idempotent re-runs).
- Step 3: read the full SOAP note.
- Step 4: extract distinct diagnosis statements from the **Assessment / A&P / Diagnoses** section, preserving laterality, "s/p", aftercare/status qualifiers.
- Step 5: for each diagnosis, use the ICD-10 MCP connector tools — `search_codes` by description, `lookup_code` for full text, `validate_code` for billability; prefer billable child codes when the parent is non-billable. Status conditions (in remission, aftercare, history of) get their own row.
- Step 6: append `## ICD-10-CM Codes` table at the end of the file. Format:
  ```
  ---

  ## ICD-10-CM Codes

  | # | Diagnosis | ICD-10-CM Code | Description |
  |---|-----------|----------------|-------------|
  ```
- Step 7: print `ICD_OK: <n> codes added` or `ICD_SKIPPED: no diagnoses found` (still exit 0 so `.docx` runs).

Skill is tolerant of MCP namespace — works whether the tools are exposed as `mcp__claude_ai_ICD-10_Codes__*` (user-level connector) or `mcp__icd10__*` (project `.mcp.json`).

### 2. Pipeline: `spawnIcdCoding(soapNoteMdPath, caseTag, patientFolderName?)`

- `claude -p "add ICD codes. Soap note: <rel-to-NOTES_DIR>." --model <soapModel> --dangerously-skip-permissions`
- `cwd: NOTES_DIR`
- Regex-scan stderr/stdout for `Needs authentication`, `401`, `unauthorized`, MCP connection errors → emit `service-warning` IPC.
- On `close` (**any** code, success or fail): always call `spawnDocxConversion(soapNoteMdPath, caseTag, patientFolderName)`. ICD failure must not block `.docx` — best-effort.

### 2b. Status window label

Add a new in-flight status `coding_icd` to `STATUS_LABELS` in `main.js` (`'Adding ICD codes...'`) and set it at the start of `spawnIcdCoding` — for the single-patient case via `updateRecordingStatus(caseTag, 'coding_icd')`, for multi-patient via `updatePatientStatus(caseTag, patientFolderName, 'coding_icd')`. Add a matching `.status-coding_icd` CSS rule in `renderer/status.css` that reuses the existing in-flight purple/pulse styling.

Resulting status timeline visible in the status window:

```
transcribing → generating_note → coding_icd → converting → completed
                                                 ↑
                                       (multi-patient: per-patient row;
                                        single-patient: parent stays on
                                        generating_note until coding_icd
                                        flips it)
```

### 3. Wiring changes in `main.js`

Replace the three direct `spawnDocxConversion(<soapNote>, ...)` call sites with `spawnIcdCoding`:

- [main.js:407](../../main.js#L407) — single-patient SOAP success
- [main.js:421](../../main.js#L421) — multi-patient subfolder loop
- [main.js:995](../../main.js#L995) — pre-chart edit-note success (diagnoses may have changed)

The transcript `.docx` conversion (line 332) stays unchanged.

### 4. MCP config fallback: `notes-claude/.mcp.json`

Bundle a project-scope MCP config file:

```json
{
  "mcpServers": {
    "icd10": {
      "type": "http",
      "url": "https://hcls.mcp.claude.com/icd10_codes/mcp"
    }
  }
}
```

`.mcp.json` lives at the project root (`<NOTES_DIR>/.mcp.json`), not inside `.claude/`. The skills-sync currently copies `notes-claude/` → `<NOTES_DIR>/.claude/`. Add a small `ensureMcpConfig(notesDir)` function that writes `<NOTES_DIR>/.mcp.json` from a constant in `main.js` next to each of the three `copyDirSync(CLAUDE_CONFIG_SRC, …)` call sites (lines 1083, 1235, 2165).

### 5. Failure surfacing

Per user preference: warn only on MCP auth/connector errors. Silent on "no diagnoses found" or model glitches — the `.md` (without codes) still becomes `.docx` and the case completes normally.

## DB integration (added 2026-05-15)

Once the SQLite state store ([2026-05-15-rs-sqlite-state-store.md](2026-05-15-rs-sqlite-state-store.md)) is in place, the ICD step participates the same way every other Claude job does: one `processing_events` row per spawn, bracketed by `startEvent` + `finishEvent` calls inside `spawnIcdCoding`. Nothing about the skill or its prompt contract changes — this is purely a wiring change on the main-process side.

### What `spawnIcdCoding` writes to the DB

`spawnIcdCoding` goes through the shared `spawnClaude` wrapper just like the other four Claude jobs (soap / template-create / template-update / prechart). The wrapper already parses `--output-format stream-json` and surfaces `usage.*`, `total_cost_usd`, `num_turns`, `duration_ms` to `onClose` — once the state-store plan's "forward full `result` event as 4th `onClose` arg" change lands, the ICD spawn picks it up for free.

Per-spawn DB pattern (mirrors the other stages in the state-store plan):

```js
let eventId = null
try {
  eventId = events.startEvent({
    case_id: caseId,                       // resolved from soapNoteMdPath → cases.soap_note_path
    job_kind: 'icd',                       // <-- new value in the job_kind enum
    model_used: soapModel,                 // same model as the soap step
    related_doctor_id: case.doctor_id,     // for filtering "ICD spend per doctor"
    started_at: nowIso()
  })
} catch (e) {
  log(`[db] startEvent failed for icd: ${e.message}`)
}
```

On close (best-effort — DB write failure must not break the pipeline):

```js
try {
  if (eventId) events.finishEvent(eventId, {
    status:               code === 0 ? 'success' : (isMcpAuthError ? 'rate_limited' : 'failed'),
    input_tokens:         resultEvent?.usage?.input_tokens,
    output_tokens:        resultEvent?.usage?.output_tokens,
    cache_read_tokens:    resultEvent?.usage?.cache_read_input_tokens,
    cache_created_tokens: resultEvent?.usage?.cache_creation_input_tokens,
    cost_usd:             resultEvent?.total_cost_usd,
    num_turns:            resultEvent?.num_turns,
    duration_ms:          resultEvent?.duration_ms,
    error_message:        code === 0 ? null : errText.slice(0, 1024),
    finished_at:          nowIso()
  })
} catch (e) {
  log(`[db] finishEvent failed for icd: ${e.message}`)
}
```

Note that `spawnIcdCoding` always proceeds to `spawnDocxConversion` regardless of exit code — that produces a separate `docx` row, unchanged from the state-store plan. The case row's status timeline becomes:

```
recording → transcribing → generating_note → coding_icd → converting → completed
```

`coding_icd` is set on the parent `cases.status` (single-patient) or per-patient row (multi-patient) — same surfaces that today update via `updateRecordingStatus` / `updatePatientStatus`. The state-store plan's status enum already includes the in-flight stages; `coding_icd` joins them.

### Schema impact

Zero schema changes. The state-store plan already lists `'icd'` as a valid `job_kind` value and explicitly notes the ambiguity around whether ICD is a discrete spawn (it is — see this plan) or runs inline inside `generate-note` (it doesn't). That open question is resolved by the design here: ICD **is** a discrete spawn between SOAP and DOCX. When the state-store implementation PR lands, it should drop the "Risk #7 — ICD step ambiguity" note from its risks section (or convert it to a back-reference to this plan).

### Sequencing

1. **First:** state-store plan lands on `develop` (creates `db/`, migrations, `getDb()`, `spawnClaude` forwards `resultEvent`).
2. **Then:** ICD branch merges to `develop`. The merge adds `spawnIcdCoding` *with* DB writes already wired — no follow-up PR to retrofit token logging.

If the ICD branch needs to merge first for any reason, the spawn ships without DB writes (it still works — best-effort logging to `app.log` continues via `spawnClaude`'s usage line). The state-store PR then adds the `startEvent` / `finishEvent` bracket as part of its "every spawn site emits events" checklist — `spawnIcdCoding` is the sixth site in that list.

### Verification (additions to the existing test plan)

- After a recording with diagnoses present, `SELECT job_kind, status, cost_usd FROM processing_events WHERE case_id = ?` returns rows in order: `transcribe`, `soap`, `icd`, `docx`, `docx` (transcript + soap docx — two rows expected per the state-store plan).
- After Pre-chart on a case whose diagnoses changed, a new `icd` row appears, followed by a new `docx` row. The existing `soap` row from the original run is untouched (Pre-chart is an `edit-note` skill run, recorded as `job_kind='prechart'`).
- ICD connector auth failure → `processing_events.status = 'failed'`, `error_message` contains the auth/MCP detail. Pipeline still completes (case row reaches `completed`).
