# SQLite state store

## Context

The app today uses three sources for state:

1. **The filesystem** — case folders under `<NOTES_DIR>/Cases/` are walked at runtime to answer "what cases exist?", "what's the latest soap note for case X?", etc. (see [findRecentPatientCases](../../main.js) at [main.js:810](../../main.js#L810), [detectPatientFolders](../../main.js#L1156), [findExistingSoapNote](../../main.js#L856)).
2. **`settings.json`** — `doctors[]` is the canonical doctor registry, plus app preferences (audio device, models, etc.).
3. **`app.log`** — append-only diagnostic log. The only place where token usage, durations, and per-stage events live today (since the [`spawnClaude` wrapper](../../main.js#L374) was introduced).

This works but it's already painful:

- The pre-chart "recent cases" dropdown re-walks the whole Cases tree on every open.
- Token cost per case is impossible to answer without grepping `app.log`.
- The floating status window ([status.js](../../renderer/status.js)) only sees in-memory `sessionRecordings`; it goes blank between app restarts.
- Phase 2 features (CDI, evaluations, provider queries) all need queryable per-case state that has nowhere to live.

**Goal:** introduce SQLite as a metadata + index store. Files on disk remain the canonical artifacts (transcript.md, *_soap_note.md, .docx) — the DB stores **references to those files plus structured metadata about them**. Like a photo library: pixels on disk, EXIF + albums + tags in the DB.

Out of scope for this plan: changing skill prompts, moving file artifacts into the DB as blobs, swapping any UI surface (the plan flags candidates but defers the swap).

---

## Guiding principles

1. **DB augments the filesystem, never replaces it.** A blown-away `app.db` must be reconstructable (best-effort) from the existing file layout. The pipeline must keep running if the DB is unreachable.
2. **Non-blocking writes.** Every DB write site wraps in `try/catch` and logs on failure. The same pattern as the existing "best-effort" pipeline steps — a failed `INSERT` never breaks transcription or note generation.
3. **One writer, one connection per process.** `better-sqlite3` in main.js is synchronous and fast (single C connection, no async layer); the Python helper uses stdlib `sqlite3` only where Python genuinely needs to read or write directly. All writes go through main.js by default; Python writes are added only when a real use case appears.
4. **WAL mode + busy_timeout.** Concurrent readers, one writer at a time. WAL is on disk in `<NOTES_DIR>` so multi-process reads (status window child renderer, future Python workers) don't block each other.
5. **Schema versioned by an integer `user_version`.** Migrations run idempotently at startup. No `node-migrate` / `umzug` — vanilla SQL files numbered `001_*.sql`, `002_*.sql`.

## Schema (v1)

Three tables in v1. Each column is justified — the schema is small on purpose; adding a column later is cheap, removing one is not.

### `doctors`

```sql
CREATE TABLE doctors (
  id              TEXT PRIMARY KEY,           -- preserved from settings.json (Date.now() string)
  name            TEXT NOT NULL,              -- full display name e.g. "Dr. Jane Smith"
  lastname        TEXT NOT NULL,              -- sanitized, lowercase — file/folder naming key
  specialty       TEXT,                       -- free text, nullable; reserved for Phase 2 CDI
  template_path   TEXT,                       -- absolute path to the template .md (may be null if doctor was added without one)
  enable_cdi      INTEGER NOT NULL DEFAULT 0, -- 0/1; Phase 2 — drives whether CDI runs for this doctor
  created_at      TEXT NOT NULL,              -- ISO8601 UTC
  updated_at      TEXT NOT NULL               -- ISO8601 UTC
);

CREATE UNIQUE INDEX idx_doctors_lastname ON doctors (lastname);
```

**Rationale:**
- `id` stays `TEXT` (not autoincrement int) because every existing `settings.json` doctor record already has a stringified `Date.now()` id, and the renderer code at [doctor select](../../renderer/renderer.js) compares ids directly. Preserving them is the cheapest migration.
- `lastname` is duplicated rather than computed because it's the join key for templates, file paths, and the legacy `extractLastname()` parser — caching it lets us skip the regex everywhere.
- `enable_cdi` shipped now (default 0) rather than added in Phase 2 because adding a column to a populated table on production installs costs a migration we can avoid.
- `specialty` is reserved for CDI rule-routing (different specialties have different documentation standards). Nullable now; populated in Phase 2 by either a settings UI or auto-inferred from template content.

### `sessions`

```sql
CREATE TABLE sessions (
  id              TEXT PRIMARY KEY,           -- UUID v4 generated by main.js in start-session
  session_folder  TEXT NOT NULL UNIQUE,       -- absolute path to the date-folder under Cases/
  doctor_id       TEXT,                       -- doctor chosen at start-session; null if doctor was later deleted
  started_at      TEXT NOT NULL,              -- ISO8601 UTC — when start-session fired
  ended_at        TEXT,                       -- ISO8601 UTC — when stop-session fired; null while active
  case_count      INTEGER NOT NULL DEFAULT 0, -- denormalised cache: total cases ever attached to this session
  failed_count    INTEGER NOT NULL DEFAULT 0, -- denormalised cache: cases whose final status was 'failed'
  created_at      TEXT NOT NULL,
  updated_at      TEXT NOT NULL,
  FOREIGN KEY (doctor_id) REFERENCES doctors(id) ON DELETE SET NULL
);

CREATE INDEX idx_sessions_started_at ON sessions (started_at DESC);
CREATE INDEX idx_sessions_doctor     ON sessions (doctor_id, started_at DESC);
```

**Rationale:**
- A session is what the user opens with **Start Session** and closes with **Stop Session**. The on-disk `session_folder` (e.g. `Cases/2026-05-15/`, `Cases/2026-05-15(2)/`) already represents this 1:1 — the DB row just makes it queryable.
- `doctor_id` is captured at session-start (not per-case) because the existing UI fixes a single doctor for the whole session via the picker. If multi-doctor sessions ever ship, the column becomes nullable + we read `cases.doctor_id` for per-case attribution.
- `case_count` and `failed_count` are denormalised caches — they could be computed via `JOIN cases`, but the daily-summary view is the most-called UI surface and incrementing two integers on case transitions is cheap. The implementation must keep them honest (every case-status transition that crosses into terminal state updates the counters).
- `session_folder UNIQUE` is the bridge back to disk — if the DB is lost, you can rebuild session rows by scanning `Cases/*/` and reading the first case row inside each.
- No `total_duration_seconds` / `total_cost_usd` columns. Those are pure aggregates; compute on demand via `JOIN processing_events`. Adding cached aggregates here would create three places (events, sessions cache, query result) that can disagree.

**Why this was promoted into v1** (after originally being deferred): the deferred design relied on `cases.session_folder TEXT` as a denormalised group key. Once we wanted "daily summary", "Claude-limit-failure rate per session", and "doctor's cases on date X" as live queries, the missing FK forced ad-hoc string parsing of folder names. Adding the table now is cheaper than retrofitting it later.

Upload cases (`process-audio-file`) bypass start-session and have no session. Their `cases.session_id` is NULL — fine, the FK is `ON DELETE SET NULL`-compatible. Reports just split "session cases" vs "ad-hoc uploads" via `WHERE session_id IS NULL`.

### `cases`

```sql
CREATE TABLE cases (
  id                      TEXT PRIMARY KEY,           -- UUID v4 generated by main.js when the case folder is built
  patient_name            TEXT,                       -- sanitized patient identifier; null for "recording_<ts>" anonymous cases
  doctor_id               TEXT,                       -- FK to doctors.id; null if doctor was deleted (intentional — keep the case)
  session_id              TEXT,                       -- FK to sessions.id; null for upload cases (no start-session)
  case_dir                TEXT NOT NULL UNIQUE,       -- absolute path to the case folder on disk
  source                  TEXT NOT NULL,              -- 'recording' | 'upload' | 'unknown' (the latter only via reconstruction)
  mp3_path                TEXT,                       -- absolute path to the audio file
  audio_duration_seconds  REAL,                       -- audio length in seconds — record.py reports on stop; pydub probe for uploads
  audio_size_bytes        INTEGER,                    -- fs.statSync(mp3Path).size after the file is finalised in the case folder
  transcript_path         TEXT,                       -- absolute path to transcript.md
  transcript_docx_path    TEXT,                       -- absolute path to transcript.docx
  soap_note_path          TEXT,                       -- absolute path to *_soap_note.md
  soap_docx_path          TEXT,                       -- absolute path to *_soap_note.docx
  status                  TEXT NOT NULL,              -- enum below
  revision                INTEGER NOT NULL DEFAULT 1, -- 1 = initial SOAP; bumped on each successful prechart edit
  recorded_at             TEXT NOT NULL,              -- ISO8601 UTC — start of recording (or upload time for uploads)
  completed_at            TEXT,                       -- ISO8601 UTC — when soap.docx mirrored; null while pipeline runs
  last_edited_at          TEXT,                       -- ISO8601 UTC — set when prechart bumps revision; null if never edited
  created_at              TEXT NOT NULL,
  updated_at              TEXT NOT NULL,
  FOREIGN KEY (doctor_id)  REFERENCES doctors(id)  ON DELETE SET NULL,
  FOREIGN KEY (session_id) REFERENCES sessions(id) ON DELETE SET NULL
);

CREATE INDEX idx_cases_recorded_at      ON cases (recorded_at DESC);
CREATE INDEX idx_cases_doctor_recorded  ON cases (doctor_id, recorded_at DESC);
CREATE INDEX idx_cases_session          ON cases (session_id, recorded_at);
CREATE INDEX idx_cases_status           ON cases (status);
```

**Status enum** (matches existing `STATUS_LABELS` in main.js so renderer code can stay aligned):
`recording`, `transcribing`, `generating_note`, `converting`, `completed`, `failed`.

Note: when [the soap step produces multiple patient subfolders](../../main.js#L468) (`detectPatientFolders` flow), each subfolder becomes its own row in `cases`, sharing the parent's `session_id` (siblings inside the same session). The parent recording case can be marked `status='completed'` with `soap_note_path=null`; the children carry the actual note paths. Querying "all cases in this multi-patient batch" becomes `WHERE session_id = ? AND case_dir LIKE '<parent>/%'` — or just `WHERE session_id = ?` if you want the whole session.

**Rationale:**
- `id` as UUID (not file path hash) so a `case_dir` rename in the future doesn't change identity.
- `case_dir UNIQUE` is the bridge back to the filesystem — every disk lookup that today walks Cases/ can become an indexed query.
- The four `*_path` columns (mp3 + transcript md/docx + soap md/docx) are stored as explicit columns rather than one JSON blob because (a) they're queried independently (the docx mirror trigger only cares about `soap_note_path`), and (b) it lets SQLite enforce non-null where we want it.
- `transcript_docx_path` is included for symmetry with `soap_docx_path` — both are deterministic `.md` → `.docx` swaps today, but storing them explicitly unlocks an "Open transcript" UI affordance later and keeps the schema consistent.
- `audio_duration_seconds` enables the highest-value pipeline analytics: cost-per-minute-of-audio, transcription speed factor, anomaly detection (e.g. a 2-minute clip whose transcription ran for 25 minutes). record.py knows the duration on stop (frame count ÷ sample rate); uploads get a `pydub` probe in `process-audio-file`. Both nullable — historical / reconstructed rows simply won't have them.
- `audio_size_bytes` is free to capture (`fs.statSync(mp3Path).size` after the file is finalised). Lower analytical value than duration but useful for "did this MP3 land corrupt / zero-byte?" debugging.
- `revision` starts at 1 (initial SOAP) and bumps to 2, 3, … on each successful prechart edit. UI surfaces showing "v3" can read this directly instead of counting prechart events.
- `last_edited_at` is null when `revision=1`; set when prechart bumps it. Together with `revision` it's the cheapest way to answer "has this case been edited, and how recently?" without scanning `processing_events`.
- `session_id` (FK) replaces the originally-proposed `session_folder TEXT` column — see the `sessions` rationale above for why we promoted that to a real table in v1.
- `doctor_id ... ON DELETE SET NULL` because deleting a doctor in [remove-doctor IPC](../../main.js#L1977) shouldn't tank case history. Same `SET NULL` policy applies to `session_id` — deleting a session row (today, never; tomorrow, maybe a "clear my history" feature) shouldn't orphan the cases.

### `processing_events`

```sql
CREATE TABLE processing_events (
  id                  INTEGER PRIMARY KEY AUTOINCREMENT,
  case_id             TEXT,                    -- FK; null for case-less jobs (template create/update)
  job_kind            TEXT NOT NULL,           -- 'transcribe' | 'soap' | 'docx' | 'prechart' | 'template_create' | 'template_update' | 'icd' (future)
  related_doctor_id   TEXT,                    -- for template_create / template_update / prechart, who the job is for
  status              TEXT NOT NULL,           -- 'started' | 'success' | 'failed' | 'rate_limited' | 'cancelled'
  model_used          TEXT,                    -- e.g. 'claude-sonnet-4-6'; null for non-Claude jobs
  effort              TEXT,                    -- 'max' | 'high' | null
  input_tokens         INTEGER,
  output_tokens        INTEGER,
  cache_read_tokens    INTEGER,
  cache_created_tokens INTEGER,
  cost_usd            REAL,                    -- decimal cost — from stream-json `total_cost_usd`
  num_turns           INTEGER,
  duration_ms         INTEGER,                 -- from stream-json `duration_ms`, or wall-clock for non-Claude jobs
  error_message       TEXT,                    -- truncated to ~1KB to avoid runaway rows
  backup_path         TEXT,                    -- prechart only: absolute path to the *_soap_note_backup_<ts>.md created by the edit-note skill
  started_at          TEXT NOT NULL,
  finished_at         TEXT,                    -- null while running
  FOREIGN KEY (case_id) REFERENCES cases(id) ON DELETE CASCADE,
  FOREIGN KEY (related_doctor_id) REFERENCES doctors(id) ON DELETE SET NULL
);

CREATE INDEX idx_events_case          ON processing_events (case_id, started_at);
CREATE INDEX idx_events_kind_started  ON processing_events (job_kind, started_at DESC);
CREATE INDEX idx_events_doctor_kind   ON processing_events (related_doctor_id, job_kind, started_at DESC);
```

**Rationale:**
- One row per `(case, job)` lifecycle — `INSERT` on start, `UPDATE` to fill in `finished_at` + result columns on close. (Not two rows for start/end — that complicates "what's the latest status of stage X?" queries.)
- `job_kind` includes `template_create`, `template_update`, `prechart` because they already share infrastructure (`templateJobProc` lock + `.template_job.json`); the DB inherits that lump.
- `icd` is a real spawn step coming from the in-flight [ICD-10 coding plan](2026-05-13-rs-icd-coding.md) (currently on the `icd10-coding` branch, not yet merged to `develop`). When that work lands, `spawnIcdCoding` becomes the sixth call site in the "every spawn site emits events" table below.
- Token columns mirror what the [stream-json parser already extracts](../../main.js#L391). The wrapper logs them today — the DB write is the same data going to a second sink.
- `backup_path` is set only for `job_kind='prechart'` rows. The `edit-note` skill prints `BACKUP_OK: <abs-path>` in its Step 9 summary — `spawnPrechartJob` parses that line out of `resultText` and writes it here. Defensive fallback: if parsing fails, glob `<case_dir>/*_soap_note_backup_*.md` for the most-recent file modified after `started_at`. Querying the full edit history for a case is then `SELECT started_at, backup_path FROM processing_events WHERE case_id=? AND job_kind='prechart' ORDER BY started_at`.
- `duration_ms` answers per-stage timing questions natively (transcription wall-clock, soap-gen wall-clock, ICD wall-clock, docx wall-clock). No separate "stage timing" columns on `cases` — they would duplicate this. Sum-per-case via `SELECT SUM(duration_ms) FROM processing_events WHERE case_id=?`.

## Module layout

```
db/
  init.js               <-- main.js side; exports `getDb()` singleton, opens app.db, runs migrations, applies pragmas
  doctors.js            <-- CRUD: listDoctors(), getDoctor(id), upsertDoctor(doctor), removeDoctor(id)
  sessions.js           <-- CRUD: startSession({...}) → id; endSession(id); bumpSessionCounters(id, {failed}); getSession(id), listRecentSessions(limit)
  cases.js              <-- CRUD: createCase(...), updateCasePaths(id, paths), setCaseStatus(id, status), bumpCaseRevision(id, backupPath), getCase(id), listRecentCases(limit), getCasesByDoctor(...)
  events.js             <-- startEvent({...}) → returns eventId; finishEvent(eventId, {...}); listEventsForCase(caseId)
  migrations/
    001_init.sql        <-- creates v1 schema; sets user_version=1
python/
  db_helper.py          <-- thin wrapper around stdlib sqlite3; opens read-only by default; ONLY used by future workers that need direct DB access
```

**Initial Python use:** none. Every existing Python child (transcribe.py, md_to_docx.py, record.py, extract_attachments.py) is short-lived and already communicates results to main.js via stdout exit codes. Main.js writes the DB row in the spawn `close` handler — Python doesn't touch the DB. `db_helper.py` is scaffolded but unused in v1; it ships so Phase 2 Python workers (CDI rule engine, embedding indexers, etc.) have a documented entry point.

**Singleton pattern in `init.js`:**
```js
let _db = null
function getDb() {
  if (_db) return _db
  const dbPath = path.join(NOTES_DIR, 'app.db')
  _db = new Database(dbPath)
  _db.pragma('journal_mode = WAL')
  _db.pragma('foreign_keys = ON')
  _db.pragma('busy_timeout = 5000')
  runMigrations(_db)
  return _db
}
```

`getDb()` is called lazily — the first time any caller (doctors.js, cases.js, events.js) needs the connection. This means setup-time code paths (e.g. the folder-setup view before `NOTES_DIR` is even chosen) don't open the DB. The connection lives until app quit.

### Init + migrations

Migrations live under `db/migrations/` as numbered SQL files. `runMigrations()` reads `PRAGMA user_version`, replays only the files whose number is `> user_version` inside a transaction, then bumps `user_version`.

For v1 there is exactly one file (`001_init.sql`). Future schema changes ship new files (`002_add_cdi_flags.sql`, etc.) — never edited in place.

**Where init is wired:**

`app.whenReady()` ([main.js:1219](../../main.js#L1219)) already has a block that runs when `NOTES_DIR` is configured (sync `.claude`, hide internals, clear stale template job). Add `getDb()` to that block, after `loadPaths(savedPath)` so `NOTES_DIR` resolves. If `NOTES_DIR` isn't set yet (first launch), the DB just doesn't open until the user picks a folder via `change-notes-dir` — that handler also calls `getDb()` after the new path is wired.

DB failures at init log a warning and **do not throw**. The app continues with the DB unavailable; all `try/catch` write sites become no-ops.

## Migrating existing state

### `doctors[]` → `doctors` table

One-time migration runs the first time `getDb()` opens a DB with `user_version = 0` after a non-empty `settings.json.doctors` is present. Logic:

```js
function migrateDoctorsFromSettings(db) {
  const settings = readSettings()
  const doctors = settings.doctors || []
  if (doctors.length === 0) return

  const insert = db.prepare(`INSERT OR IGNORE INTO doctors
    (id, name, lastname, template_path, enable_cdi, created_at, updated_at)
    VALUES (@id, @name, @lastname, @template_path, 0, @ts, @ts)`)
  const ts = new Date().toISOString()
  const txn = db.transaction(rows => { for (const r of rows) insert.run(r) })
  txn(doctors.map(d => ({
    id: d.id,
    name: d.name,
    lastname: extractLastname(d.name) || d.name.toLowerCase(),
    template_path: d.templatePath || null,
    ts
  })))

  // Move settings.json to read-only backup; strip doctors[] from live settings
  const { doctors: _, ...rest } = settings
  fs.writeFileSync(path.join(NOTES_DIR, 'settings.doctors.backup.json'),
                   JSON.stringify(doctors, null, 2))
  writeSettings(rest)
}
```

After migration:
- `settings.json` no longer carries `doctors[]`. Code that called `readSettings().doctors` must switch to `listDoctors()` from the DB (see "Write points" below).
- The backup file `settings.doctors.backup.json` is kept indefinitely as an escape hatch. It is **not** consulted by app code — purely a hand-recovery resource.
- `DEFAULT_SETTINGS` ([main.js:118](../../main.js#L118)) drops the `doctors: []` key (kept just for backward-compat reads; removed entirely after one release cycle).

### Cases reconstruction

For users with an existing notes-dir on day 1 of this change, we **do not** backfill every historical case into `cases`. Reasons:
- Walking Cases/ at install time bloats first launch.
- Most historical metadata is lost (exact recording start time, doctor at the time of recording, model used) — backfilled rows would be best-guess at best.
- The DB is augmenting going forward; the existing filesystem is still walkable for any retroactive query.

Instead: on first DB open, log a one-line summary `[db] existing cases on disk: N (not backfilled)` and move on. New cases from this version onward land in the DB.

If a UI surface ever needs historical cases queryable, write a one-off `npm run backfill-cases` script — kept out of normal startup.

### Settings.json — what stays vs moves

| Key | Where it lives after v1 | Why |
|---|---|---|
| `autoRecord`, `manualDeviceSelection`, `selectedDeviceIndex` | settings.json | Audio config — user-editable, fine in JSON |
| `soapModel`, `templateModel`, `templateEffort` | settings.json | Model choices — single-value config, fine in JSON |
| `doctors[]` | **moved to DB** | Real entities with relationships (cases.doctor_id) |
| `ELEVENLABS_API_KEY` (in `.env`) | .env | Secrets shouldn't be in the same store as queryable data |
| `NOTES_DIR_PATH` (in `.env`) | .env | Bootstrap — `.env` is read before NOTES_DIR is known |

`.template_job.json` is unaffected — it's runtime IPC state, not historical data. Could be replaced by a `processing_events` row queried with `WHERE status='started' AND job_kind IN ('template_create','template_update','prechart')` later, but that's an optional follow-up.

## Write points (main.js)

Every spawn function gets two DB calls bracketing it. Wrapped in `try/catch`, logged on failure, never throws into the pipeline. Pattern is identical across stages so adding a new stage is trivial.

Per spawn:

```js
let eventId = null
try {
  eventId = events.startEvent({
    case_id: caseId,
    job_kind: 'soap',
    model_used: soapModel,
    related_doctor_id: null,
    started_at: nowIso()
  })
} catch (e) {
  log(`[db] startEvent failed for soap: ${e.message}`)
}

spawnClaude({
  // ...
  onClose(code, errText, resultText, parsedResultEvent) {  // see "Token capture" below
    try {
      if (eventId) events.finishEvent(eventId, {
        status: code === 0 ? 'success' : (isRateLimited ? 'rate_limited' : 'failed'),
        input_tokens:         parsedResultEvent?.usage?.input_tokens,
        output_tokens:        parsedResultEvent?.usage?.output_tokens,
        cache_read_tokens:    parsedResultEvent?.usage?.cache_read_input_tokens,
        cache_created_tokens: parsedResultEvent?.usage?.cache_creation_input_tokens,
        cost_usd:             parsedResultEvent?.total_cost_usd,
        num_turns:            parsedResultEvent?.num_turns,
        duration_ms:          parsedResultEvent?.duration_ms,
        error_message:        code === 0 ? null : (errText.slice(0, 1024)),
        finished_at:          nowIso()
      })
    } catch (e) {
      log(`[db] finishEvent failed for soap: ${e.message}`)
    }
    // ... existing logic
  }
})
```

|---|---|---|---|---|
| [spawnTranscription](../../main.js#L329) | `transcribe` | yes | none (Python child) | duration = wall clock; status from exit code |
| [spawnSoapGeneration](../../main.js#L432) | `soap` | yes | from stream-json | watch for multi-patient case → still ONE soap event for the parent recording |
| [spawnDocxConversion](../../main.js#L498) | `docx` | yes | none | runs twice per case (transcript + soap); two rows OK — query by `job_kind='docx'` returns both |
| [spawnTemplateCreation](../../main.js#L576) | `template_create` | null | from stream-json | `related_doctor_id` set after doctor row is upserted on success |
| [spawnTemplateUpdate](../../main.js#L692) | `template_update` | null | from stream-json | `related_doctor_id` from lookup |
| [spawnPrechartJob](../../main.js#L928) | `prechart` | yes (looked up by `case_dir`) | from stream-json | also re-runs `spawnDocxConversion` → that's a separate `docx` event |
| `spawnIcdCoding` (from [ICD-10 plan](2026-05-13-rs-icd-coding.md)) | `icd` | yes | from stream-json | runs between `soap` and `docx`; always falls through to `spawnDocxConversion` regardless of exit code (best-effort, mirrors today's ARCHITECTURE.md description) |

**Where `sessions` rows are written:**

| Trigger | Insert / update |
|---|---|
| [start-session IPC](../../main.js#L1397) — after doctor is fixed and `createSessionFolder()` returns | `INSERT` into `sessions` with `started_at`, `session_folder`, `doctor_id`; capture the new `id` into the existing in-memory `activeSessionId` (new module-level var alongside `activeDoctorId`) |
| [stop-session IPC](../../main.js#L1433) | `UPDATE sessions SET ended_at=…` |
| Every `cases.status` transition to terminal `completed` or `failed` | `UPDATE sessions SET case_count = case_count + 1 (or 0 if reusing the same row), failed_count = failed_count + (status='failed' ? 1 : 0)` — i.e. the cache is updated lazily as cases reach terminal state, **not** at case creation, so retries / state regressions don't double-count |

**Where `cases` rows are written:**

| Trigger | Insert / update |
|---|---|
| `buildCaseFolder()` returns ([stop-recording](../../main.js#L1543)) | `INSERT` into `cases` with `status='transcribing'`, `doctor_id`, `session_id` (from `activeSessionId`), `mp3_path`, `source='recording'`, `recorded_at`, `revision=1` |
| record.py exits cleanly (in the `stop-recording` close handler, after MP3 is moved into the case folder) | `UPDATE cases SET audio_duration_seconds=…, audio_size_bytes=…` — duration comes from a final line record.py prints on stop (`DURATION_SECONDS: <float>`); size from `fs.statSync(mp3Path).size`. Both best-effort — failure to capture either just leaves the column NULL |
| [process-audio-file](../../main.js#L2092) | `INSERT` with `source='upload'`, `status='transcribing'`, `session_id=NULL`. Audio duration + size populated in the same handler (size from `statSync`; duration from a quick `pydub`/`ffprobe` probe — best-effort) |
| `spawnTranscription` close (success) | `UPDATE cases SET status='generating_note', transcript_path=...` |
| `spawnDocxConversion` close (success, transcript) | `UPDATE cases SET transcript_docx_path=...` (status stays — soap is the gate) |
| `spawnSoapGeneration` close (success) | `UPDATE cases SET status='converting', soap_note_path=...` |
| `spawnDocxConversion` close (success, soap) | `UPDATE cases SET status='completed', soap_docx_path=..., completed_at=...` |
| Any close with non-zero exit | `UPDATE cases SET status='failed'` |
| `spawnPrechartJob` close (success) | `UPDATE cases SET revision = revision + 1, last_edited_at = ...` — case status stays `completed`. The `processing_events` row for this run carries the `backup_path` for full history |

**Multi-patient case caveat:** when [`detectPatientFolders`](../../main.js#L1156) finds child folders, each one becomes its own `cases` row (one `INSERT` per child) sharing the parent's `session_id` and `doctor_id`. The parent's `soap_note_path` stays null; the children carry the soap paths. This mirrors the in-memory `sessionRecordings[].patients[]` structure today. The session's `case_count` increments for each terminal child — not for the parent, since the parent is just a recording container.

## Token capture

Already done — the [`spawnClaude` wrapper at main.js:374](../../main.js#L374) parses the `result` event from `--output-format stream-json` and pulls out `usage.input_tokens`, `usage.output_tokens`, `usage.cache_read_input_tokens`, `usage.cache_creation_input_tokens`, `total_cost_usd`, `num_turns`, `duration_ms`. Today these get logged once via the `[<label>][usage] …` line.

Minimal change to feed the DB: have `spawnClaude` pass the **full parsed `result` event object** through to `onClose` (today it only forwards `resultText`, which is `result.result` — the text body). Three call sites already destructure `(code, errText, resultText)` — adding a fourth positional arg is non-breaking:

```js
onClose(code, errText, resultText, resultEvent)
//                                  ^-- new — full parsed { type:'result', usage:{...}, total_cost_usd, num_turns, duration_ms, result:'...' }
```

For non-Claude jobs (transcribe, docx), there are no tokens — those columns just stay NULL. `duration_ms` for them comes from `Date.now() - startedAt` captured in the wrapper.

If a job exits without ever emitting a `result` event (Claude killed, network drop), `resultEvent` is `null` — the `?.usage?.input_tokens` lookup gives `undefined`, which `better-sqlite3` writes as NULL. No crash.

## Risks + open questions

1. **Concurrent writes from multiple processes.** WAL handles single-writer-multi-reader. Today only main.js writes; Python children don't. If a future Python worker writes, it must `BEGIN IMMEDIATE` to take the write lock — and main.js needs a `busy_timeout` (set above to 5000ms) so transient lock contention doesn't throw. **Open:** do we set a global retry policy on the main-side helpers, or rely on `busy_timeout` alone? Recommendation: rely on `busy_timeout` for v1; revisit if we see `SQLITE_BUSY` in `app.log`.
2. **Single-instance lock interaction.** [`app.requestSingleInstanceLock()`](../../main.js#L1203) already guarantees one main process. Plus WAL handles secondary readers (the renderer doesn't open the DB directly; everything goes through IPC).
3. **What if `app.db` is deleted?** Pipeline still runs (every write site try/catches). On next `getDb()` the file is recreated by `001_init.sql`; `user_version=0` → migration replays. Doctor migration from `settings.json.doctors` doesn't re-run because settings.json no longer carries `doctors[]` post-v1 — instead the helper detects empty `doctors` table + presence of `settings.doctors.backup.json` and re-imports from the backup. (If the backup is also gone: log a one-line warning and let the user re-add doctors via the Templates tab.)
4. **Backup story.** No automated backup ships in v1. SQLite + WAL files are copyable as-is when the app is closed; we add a manual `npm run backup-db` script if it ever becomes a real ask. Cases on disk are the durable record — the DB is a cache.
5. **better-sqlite3 native module across platforms.** It's a prebuilt binary; `electron-rebuild` runs as part of `npm install` already (Electron app). Verify on Windows + macOS during implementation. If prebuilds aren't available for the Electron version in use, we get a build-time failure — caught in CI before a release.
6. **Token data accuracy on rate-limited runs.** When Claude hits a usage limit, the `result` event may still emit with partial counts. The `status='rate_limited'` row will have whatever tokens were billed up to that point — acceptable for cost tracking, surprising for "did this stage complete" semantics. Worth a comment in `events.js` clarifying that `rate_limited` rows can carry partial usage.
7. **ICD step sequencing with the in-flight ICD branch.** The [ICD-10 coding plan](2026-05-13-rs-icd-coding.md) introduces `spawnIcdCoding` between `spawnSoapGeneration` and `spawnDocxConversion`. Schema accommodates it today (`job_kind` is a TEXT enum; `'icd'` is listed). If this state-store plan lands first, the ICD branch merge picks up DB writes by adding one `startEvent` / `finishEvent` bracket inside `spawnIcdCoding`. If the ICD branch merges first, the state-store implementation PR includes `spawnIcdCoding` in its "every spawn site emits events" checklist — same code, just a different sequencing point. Either way the schema is unchanged.
8. **Renderer access pattern.** Renderer never opens the DB directly. New IPC handlers (`listDoctorsViaDb`, `listRecentCasesViaDb`, `getUsageSummary`, etc.) come in the implementation PR. No new `window.api` methods are added by this plan.
